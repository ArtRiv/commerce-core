## 1. e2e in CI — optional follow-up (the fast gate is DONE)

Merged to main (PR #6): `.github/workflows/ci.yml` runs
install --frozen-lockfile -> prisma generate -> lint:check -> typecheck ->
unit tests -> build, on push to main and on every PR. No secrets, no
database, ~1-2 min. Node/pnpm pinned via .nvmrc + engines + packageManager.

Still missing: the e2e tests only ever run on my machine (161 of them now,
across eight files, ~18 min against hosted Supabase).

Two things changed since this was first written, both of which make it more
attractive: the suite grew, and the deploy proved the migrations run clean
against a database that started empty.

```
I'm working on commerce-core, a NestJS headless e-commerce backend at
c:\Users\Arthu\Desktop\code\commerce-core.

CI already exists: .github/workflows/ci.yml has one `verify` job (lint,
typecheck, 440 unit tests, build) that needs no secrets and no database.
This task adds a SECOND job that runs the 161 e2e tests against an
ephemeral Postgres service container.

Read first: .github/workflows/ci.yml (its comments explain why e2e was
left out), test/jest-e2e.json, test/support/app.ts, prisma/seed.ts.

Hard rules, each already verified:
- NEVER point a CI job at a Supabase DATABASE_URL. Every e2e suite
  TRUNCATEs shared tables, so a CI run would wipe whatever database it is
  aimed at. Ephemeral container only. (Production now lives in a SEPARATE
  Supabase project for exactly this reason — see docs/specs/deploy.md.)
- NEVER write a .env file in CI. test/payments-live.e2e-spec.ts reads
  STRIPE_SECRET_KEY from the .env FILE and runs against real Stripe for any
  value starting with sk_ that is not exactly `sk_test_offline`. Verified:
  with no .env it reports "2 skipped"; with a .env containing a placeholder
  like sk_test_dummy it wakes up and fails with "Invalid API Key". A key in
  process.env (a GitHub secret in `env:`) does NOT wake it. So pass all
  config through `env:`.
- Run e2e through `pnpm test:e2e`, never bare jest: the script sets
  NODE_OPTIONS=--experimental-vm-modules via cross-env, and without it the
  app fails to boot on the generated Prisma 7 client's dynamic import.

Already checked: the migrations are portable to stock Postgres — no
CREATE EXTENSION, no gen_random_uuid(), no Supabase roles (anon and
authenticated appear only in SQL comments), ids are TEXT generated by
Prisma. `prisma migrate deploy` + the seed ran clean against an empty
database during the deploy, so this is proven, not assumed.

What to work out:
1. Wall clock. It is ~18 min against hosted Supabase, and much of that is
   round-trip latency a localhost container does not have. MEASURE it
   before choosing the trigger — the answer decides whether this runs on
   every PR, only on PRs to main, or on workflow_dispatch.
2. The exact env the app needs to boot under test. At minimum DATABASE_URL,
   JWT_SECRET and NODE_ENV=test; APP_URL is read by StripePaymentProvider,
   which the e2e does bind (test/support/app.ts forces the Stripe keys to
   the offline sentinel). Confirm the real list empirically. Note NODE_ENV=test
   also satisfies the boot guards for Stripe, SHIPPING_TABLE and
   TRUST_PROXY_HOPS.
3. Seeding: roles and permissions are reference data the suites depend on
   and never truncate. `prisma db seed` runs `tsx prisma/seed.ts` via
   prisma.config.ts.
4. Whether the RLS deny-all posture is still worth asserting on a container
   where there is no PostgREST and no anon role to defend against.
```

## 2. Reusable across storefronts — NOT YET SPECIFIED

The stated goal: use commerce-core as the backend for more than one
storefront project, not just the first front-end.

This is NOT the same as the multi-tenancy that `claude/context.md` puts
out of v1 scope, and the difference decides the whole design — one
deployment serving many stores, versus one deployment per store off a
shared codebase. Discuss before any code: the second is nearly free today,
the first touches every table and every query.

## Optional / decided against for MVP

- **Guest cart** (sessionId alongside userId, merged on login). Real conversion
  impact, but plenty of stores require an account, and docs/specs/orders.md
  already designed the migration path. Revisit once the frontend exists.
- **Stock reservation TTL** — needs BullMQ (post-v1 in claude/context.md).
  Abandoned CREATED orders hold stock until someone cancels; manual cancel is
  the escape hatch today.
- **Coupons** — permissions exist in src/auth/authz/permissions.ts, the feature
  does not.
- **Deferred payments hardening** — verifying Stripe's amount_total against the
  order, and serialising concurrent /pay and /refund. See docs/specs/payments.md
  "Decisoes adiadas".
- **Cart cumulative quantity cap** — see docs/known-issues.md.
- **Redis storage for the throttler** — mandatory the day there is a second
  instance; today's single free instance is what keeps in-memory correct.
